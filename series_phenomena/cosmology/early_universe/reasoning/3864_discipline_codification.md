# Reasoning capture — Patch 3864: codifying the arc's process rules where they will actually be read

*Session 191, 9 Sep 2026, EU lane. Verbatim at-patch capture. Verify `scripts/3864_discipline_codification.py` (11/11).*

The founder asked whether I had changed the template or the OS, or merely written a note to myself that only this context window would remember. The honest answer was the second, in substance if not in form, and the question exposed a defect I had not seen.

The rules were written into session handovers, session logs, the frontier header and the finding documents. All of those are committed to the repository, so in one sense they persist. But the bootup sequence's Step 2 reads only the *most recent* handover, and every session writes a new one that supersedes the last. A durable process rule placed in a handover therefore leaves the read path the moment the next session closes. It stays in the repository and stops being read. That is worse than useless, because the record shows the lesson was learned while the next worker never encounters it.

Checking, there was no standing worker-discipline section in bootup.md at all. The rules had nowhere durable to live, which is why they kept ending up in handovers. So I created one, at §0.5, and added it to the Step 1 read table at priority 1.5, marked as required before doing any work. Step 1 is read every session; that is the difference between a rule and a note.

I wrote six rules and attached each one's cost record rather than stating it abstractly. Search for the mechanism a clause names before declaring the clause fails — that one cost a false negative against sound work and two wrongly annotated documents. Re-check the premise of anything carried over more than two sessions — that cost a session on a route whose premise had been withdrawn seven patches before it was named. Locate an object in the corpus before building on it — four patches were built on an order parameter nobody had confirmed existed, and the sector that supplied it had already refuted the candidate. A flagged check is not a performed check — three patches leaned on a check that the first of them had raised precisely so it would not be assumed silently. Check the log and the id counter against origin before starting — twice work was duplicated, twice new work nearly built on an unpushed base. Check whether a lane is complete before escalating against its numbers — that produced an eighty-six-order escalation on a working value.

The cost record matters more than the rule. A rule without one reads as boilerplate and gets skimmed; a rule with a date, a patch number and a consequence is a warning. I also wrote the common remedy as a single line, because all six failures have the same shape and the same fix: before reasoning forward from a clause, an item or another lane's number, spend one grep on the thing it names. Six failures, one remedy, and in every case a single search would have prevented it.

One physics-side rule went in beside them, from 3850: a derived shift is not an error bar. That one changed a number in print after five versions had carried it as a symmetric uncertainty, and it belongs with the others because the failure mode is the same — carrying an inherited framing forward without re-examining it.

What I did not do is claim this fixes the underlying problem. The rules will be read; whether they are followed is a different question, and the arc's own record is that I wrote a version of D-2 at 3854 and then violated its spirit twice in the three sessions after. Putting them in the read path is the necessary condition, not the sufficient one.
