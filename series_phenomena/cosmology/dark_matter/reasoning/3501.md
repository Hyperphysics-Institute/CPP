# Reasoning fragment — Patch 3501 (the gate did not run on the machine that matters)

next_id.py, shipped one patch ago as the mechanical guard against ID
collisions, crashed on its first real invocation on Kila6. It never ran.

Cause: Python on Windows decodes subprocess output with the locale codec
(cp1252), and this corpus's commit messages are dense with characters
cp1252 cannot represent — beta, arrows, em-dashes. The reader thread
raised UnicodeDecodeError, `.stdout` came back None, and the join failed.

This is the SECOND occurrence of this defect class in two days. The first
was `--analyze` crashing under `> file` redirection on the Greek beta,
fixed at 3175 by forcing stdout to UTF-8. I fixed the symptom there and
did not generalize: I never asked where else this container's UTF-8
default diverges from Windows' cp1252 default. The answer was "anywhere
this code reads or writes text," and subprocess decoding was the obvious
second place.

The developing-environment asymmetry is the root: I write and test in a
UTF-8 container, the founder runs on a cp1252 Windows host, so any
encoding assumption I make is untested until it reaches him. Every
text-producing or text-consuming script in this corpus is exposed. Fixed
here for next_id.py: explicit utf-8 decode of git output with
errors='replace', stdout reconfigured, and the join hardened against a
None element.

errors='replace' rather than 'strict' deliberately: a mangled character
must never stop the check. An unreadable byte in one old commit message
is not a reason to leave a patch ID unverified — the failure mode of a
gate that refuses to run is that the human proceeds without it, which is
exactly the state 3500 was written to end.

Worth stating plainly: a guard that has never executed on the target
machine is not a guard. 3500's claim to have made the check mechanical
was premature by one patch.
