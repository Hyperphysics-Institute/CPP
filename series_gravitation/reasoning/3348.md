THE JUDGMENT: fix the CLAIM, not the SENTENCE. The cheap repair was
to rewrite one sentence to say "verified by four scripts." That would
have been true today and false again at the next version bump, which
is precisely the failure mode 3347 named: verification claims rot,
because the file grows around them and nobody re-reads a sentence that
was true when written. I had already watched this happen twice in one
day (the "V0, not yet panel-reviewed" limits line at 3338; this
sentence itself across V1.0-V1.3). A third prose repair would have
been the same bet on my own future attention, which has now lost
twice.

So V1.4 states the provenance as a TABLE - four scripts, four counts,
and the one quantity that is not script-verified at all - and a
checker asserts the table against the filesystem: scripts exist,
counts equal actual check() totals, the inherited quantity stays
declared, the old phrasing cannot return. Change a script and the
paper's claim fails a test instead of quietly becoming false.

TWO THINGS I DID BECAUSE OF TODAY'S PATTERN, NOT BECAUSE THEY WERE
ASKED FOR.

First, the checker FAILED on its first run - 1/4 on check 5 - and the
paper was right, the checker was wrong: the .tex typesets filenames

fixed the checker by normalizing rather than by relaxing the check,
and left a note in the code saying so, because a test that gets
loosened the first time it fires is worthless and the temptation to
loosen it was real.

Second, I ADVERSARIALLY TESTED the rot-detector: reinserted the V1.3
sentence, confirmed check 4 fires with "REGRESSION", then restored.
An assertion nobody has ever seen fail is a decoration. This one has
now failed on purpose, once, and been shown to recover.
