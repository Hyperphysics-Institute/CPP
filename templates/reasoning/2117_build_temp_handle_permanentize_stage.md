# Reasoning — Patch 2117 (build the §6.1 temp-handle permanentize stage)

STATUS: verbatim, at-patch (Opus, 2100 protocol band by explicit TLA authorization, 24 June 2026). Build patch + tests. No physics computation.

This wires the §6.1 rule ratified in 2116 into `overnight_extraction_audit.sh`, folds the regression case into the live harness (now 34/34), removes the superseded pending stub, and updates the protocol doc's implementation-status from "tracked build item" to "built, v1-staged."

The one judgment call that shaped the whole build: stage, don't auto-apply. §6.1's auditor obligations say "corpus-wide find-replace." Read literally that is the macro rewriting committed paper files at 3 AM. But the macro's ratified v1 stance (panel 4/4) is unambiguous: it stages everything and writes only the heartbeat direct; founders and registries are TLA-applied from staging, and auto-promote "NEVER self-graduates" without explicit TLA criteria. A corpus rename touches committed papers — canonical. So auto-rewriting them would be me deciding the machine has earned the right to edit the corpus, which is exactly the call the protocol reserves to TLA (the §4.1 founders principle, generalized). I implemented v1-staged: assign + stage a ready-to-run rename script + stage the theorem-registry registrations (through the existing phase-4 registry/*.delta channel), and let TLA apply in the morning. The alias map I do write directly, because it is operational auditor bookkeeping with grace-window expiry — the same category as the heartbeat, not a paper or a registry. This is safe precisely because of the design's signature property: the handle is already unambiguous, so a staged-but-unapplied rename still resolves via the alias map. Auto-apply is left as a documented v2 graduation for TLA. I updated §6.1's implementation-status and obligation 3 to say so, rather than let the prose imply an auto-rewrite the build deliberately does not do.

Claim-driven, not handle-parsed — the parsing-ambiguity fix. Family is read from the pending claim (`family:DS`), never parsed from the handle. This matters because families can end in digits (THEO-SF-4), so `THEO-SF-4-TMP-p..` is ambiguous between family SF-4 and family SF with display-guess 4. Driving assignment off the claim's declared family sidesteps that entirely. A handle found in the corpus with no matching claim can't have its family guessed safely, so it is flagged REVIEW:ORPHAN rather than assigned — honest over clever.

Determinism + reserved-slot safety. Within a family, handles sort by patch then seq, so assignment is stable and reproducible across re-runs (idempotent staging). Next number is max-present + 1 with a skip over any taken-or-reserved number (theo_taken greps the registry, so a RESERVED row is treated as taken). I chose append-after-max rather than lowest-free-gap: gaps and reservations may be intentional, and never reusing a gap is the safer default. Verified in a live smoke test (registry with THEO-DS-6 + THEO-DS-9 RESERVED → assigned DS-10/DS-11, skipping the reserved 9).

Phase ordering + non-interference with the tested phase 4. Permanentize runs before phase 4 and consumes (strips) the TMP claim lines from the pending files, so phase 4 sees only genuine registry deltas and its 12 existing assertions are untouched. Added a one-line defensive skip in phase 4 for any stray TMP line so `--only registry` can't false-flag a temp claim as REVIEW:SCHEMA. The corpus grep excludes infra dirs (.git, Development, Registries_pending, scripts, templates) so format-examples in the protocol doc and fixtures in the test scripts never get picked up as real handles.

The 2116 pending stub asserted against an auto-apply behavior that the v1 build deliberately does not do; I rewrote the cases for v1-staged reality (plan staged, two distinct permanents for two same-guess handles on different patches, alias entries, registry registrations, pending consumed, papers deliberately unchanged, heartbeat perm:2) and put them in an isolated second scratch so the original 20 stay pristine. Removed the pending stub (its probe contract — `theo_alias_map` in the macro — is now met, which is what auto-activates the case). Existing harness re-run confirms 34/34, with the full no-`--only` macro run also green.
