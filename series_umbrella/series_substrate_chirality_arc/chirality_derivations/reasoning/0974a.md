## Turn 2 — the renumber, on the founder's instruction *"Please renumber patch 0975 to 0974a, as the next window has already used 0975."*

> Found a real problem. `next_id.py` matches `^(0\d{3})\s+` — a suffixed ID has a letter where it
> expects whitespace.

> Confirmed — a bare `0974a` is invisible to the collision gate. Doing the renumber and teaching the
> gate to see it, since shipping the first suffixed ID with a blind gate would defeat the rule it
> exists to enforce.

> The rename is mechanical, but it introduced a genuine hazard I wasn't willing to ship […] I tested
> it: `0974a SESSION…` matched nothing. The first suffixed patch in this block would have been
> invisible to the very gate that exists to prevent collisions — and this renumber exists because of
> a collision. So I taught the parser the form in the same patch (`[a-z]?`), verified before and
> after, and recorded why in a comment at the regex. **An ID the gate can't see is an ID the gate
> can't protect.**

> One honest caveat on the numbering: `next_id.py` now reports highest used 974, next free 975 —
> because 0975 isn't on origin yet; it's in the other window, unpushed. My registry line records next
> free 0976, which is the true state. The script can only see what's pushed, so the registry is right
> and the script is behind until that window lands. **Worth knowing so nobody "corrects" the registry
> back.**

> Two things for whoever holds the other window: 0974a is a suffixed ID and the first in the 09xx
> block — if their tooling parses patch numbers, it needs the same `[a-z]?` allowance. And once their
> 0975 is pushed, `next_id.py` will agree with the registry at 0976.
